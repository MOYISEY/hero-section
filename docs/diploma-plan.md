# Проверка дипломного проекта NeuralBrief

Тема: «Разработка веб-приложения с интеграцией нейронной сети (LLM) для диалога с клиентом и формирования технического задания».

## 1. Введение и пояснительная записка

### Статус

Требование относится к текстовой части диплома. В приложении функциональная база есть, но раздел нужно оформить в пояснительной записке.

### Готовая формулировка актуальности

В современных IT-проектах значительная часть ошибок возникает на этапе первичного сбора требований. Клиент часто формулирует задачу неполно, использует бытовые описания вместо технических терминов, не указывает целевую аудиторию, функциональные ограничения, сроки и критерии готовности. В результате менеджеру и разработчику требуется проводить дополнительные интервью, уточнять детали и вручную структурировать информацию в техническое задание.

Использование больших языковых моделей (LLM) позволяет автоматизировать часть этого процесса. Нейросеть может вести диалог с клиентом на естественном языке, задавать уточняющие вопросы, выявлять недостающие данные, классифицировать требования и формировать черновик технического задания. Это снижает нагрузку на менеджера, ускоряет старт проекта и повышает полноту исходных требований.

Разрабатываемое веб-приложение NeuralBrief направлено на решение данной задачи: оно объединяет чат с LLM, генерацию ТЗ, сохранение проекта, CRM-логику ролей и передачу задачи от клиента к менеджеру и разработчику.

### Проблема

Проблема исследования заключается в отсутствии удобного инструмента, который позволяет клиенту без технической подготовки описать будущий веб-проект, а системе — автоматически преобразовать этот диалог в структурированное техническое задание.

### Объект

Объект исследования — процесс сбора, уточнения и структурирования требований к веб-приложению на этапе первичного общения с клиентом.

### Предмет

Предмет исследования — методы интеграции LLM в веб-приложение для ведения диалога с клиентом, извлечения требований и формирования технического задания.

### Методы

- анализ предметной области и существующих подходов к сбору требований;
- проектирование архитектуры веб-приложения;
- проектирование UX/UI сценариев диалога;
- интеграция LLM через API;
- prompt engineering;
- проектирование базы данных;
- функциональное и сценарное тестирование.

### Ожидаемый эффект

- сокращение времени первичного сбора требований;
- повышение полноты и структурированности ТЗ;
- уменьшение количества повторных уточнений;
- единый workflow: клиент → менеджер → разработчик;
- сохранение истории диалога и результатов проекта.

## 2. Исследование и технологический стек

### Статус реализации

В проекте реализовано.

### Используемый стек

- Frontend и backend: Next.js App Router;
- язык: TypeScript;
- UI: React, Tailwind CSS, Radix UI, lucide-react, sonner;
- LLM-интеграция: Vercel AI SDK, Groq API, модель `llama-3.3-70b-versatile`;
- база данных: PostgreSQL;
- авторизация: cookie-based session + роли;
- хранение данных: таблицы users, projects, tasks, task_assignments, notifications, chat_sessions, chat_messages, project_chats, project_chat_messages, project_reviews, audit_log.

### Обоснование выбора

Next.js выбран, так как позволяет объединить клиентский интерфейс, серверные API routes и SSR/динамические страницы в одном проекте. TypeScript снижает количество ошибок за счёт статической типизации. PostgreSQL подходит для хранения связанных сущностей: пользователей, проектов, задач, сообщений и уведомлений. Vercel AI SDK упрощает потоковую интеграцию LLM, а Groq обеспечивает быстрый ответ модели.

### Архитектура

Приложение построено по модульной архитектуре:

- UI-компоненты находятся в `components`;
- страницы находятся в `app`;
- API endpoints находятся в `app/api`;
- схема базы данных находится в `database/schema.sql`;
- бизнес-логика ролей и паролей находится в `lib/auth.ts`.

Основной поток данных:

1. Клиент общается с AI в `/chat`.
2. История сохраняется через `/api/sessions`.
3. Черновик ТЗ формируется на странице `/brief`.
4. Клиент отправляет ТЗ менеджеру через `/api/briefs/send-to-manager`.
5. Менеджер принимает или отклоняет заявку через `/api/manager/projects`.
6. При принятии создаётся задача разработчику.
7. Разработчик обновляет статус и GitHub repository через `/api/developer/tasks`.
8. Менеджер закрывает задачу после проверки, клиент получает результат в личном кабинете.
9. Клиент подтверждает проект, ставит оценку, проект архивируется.

### Безопасность и конфиденциальность

В проекте реализованы:

- хеширование паролей через PBKDF2 (`lib/auth.ts`);
- проверка ролей пользователя на API-уровне;
- хранение API-ключа Groq только в переменной окружения `GROQ_API_KEY`;
- ограничение доступа разработчика только к назначенным задачам;
- фильтрация уведомлений по пользователю;
- soft-delete уведомлений и пользователей;
- запрет входа заблокированных пользователей;
- изолированные чат-каналы по ролям;
- audit log для действий директора;
- отсутствие hardcode API-ключей в исходном коде.

## 3. Проектирование UX/UI и диалоговой логики

### Статус реализации

Реализовано частично в интерфейсе и может быть описано в дипломе.

### Сценарий общения

1. AI приветствует пользователя и просит описать проект.
2. Пользователь пишет свободное описание.
3. AI задаёт по одному уточняющему вопросу.
4. Система отслеживает прогресс по этапам:
   - тип проекта;
   - цели;
   - аудитория;
   - функциональность;
   - дизайн;
   - сроки и формат.
5. После накопления достаточного контекста пользователь переходит к формированию ТЗ.

### Пример уточняющих вопросов

- Какой тип проекта нужно создать: сайт, CRM, лендинг, интернет-магазин или веб-сервис?
- Какую основную бизнес-задачу должен решить проект?
- Кто является целевой аудиторией?
- Какие основные функции должны быть в первой версии?
- Есть ли предпочтения по стилю, цветам и визуальному направлению?
- Нужна ли авторизация и роли пользователей?
- Нужно ли подключение внешних сервисов или API?
- Какие сроки и ограничения по проекту?
- Какие данные нужно хранить?
- Какой результат считается готовым проектом?

### Состояние диалога

Состояние диалога хранится на клиенте в `localStorage` и дополнительно сохраняется в PostgreSQL через `/api/sessions`.

### Структура результата

Итоговое ТЗ содержит:

- название проекта;
- цель проекта;
- аудиторию;
- функциональные требования;
- нефункциональные требования;
- дизайн-рекомендации;
- структуру страниц;
- технический стек;
- этапы реализации;
- критерии готовности.

## 5. Интеграция нейросети

### Статус реализации

Реализовано.

### Где реализовано

Файл: `app/api/hero-chat/route.ts`.

Используется:

- `@ai-sdk/groq`;
- `streamText`;
- системный prompt;
- модель `llama-3.3-70b-versatile`;
- потоковая отдача ответа в UI.

### Шаблон prompt

В системном prompt задано поведение ассистента:

- отвечать кратко;
- задавать один уточняющий вопрос за раз;
- не принимать мусорные данные;
- не формировать ТЗ без минимального контекста;
- поддерживать русский, казахский и английский язык.

## 7.1. CRM, уведомления, коммуникации и директорский контроль

### Статус реализации

Реализовано.

### Уведомления

В системе реализована лента уведомлений для менеджера и разработчика:

- кнопка удаления отдельного уведомления;
- кнопка «Очистить все»;
- визуальное различие прочитанных уведомлений;
- API `/api/notifications` для действий `mark_as_read`, `delete`, `clear_all`;
- soft-delete через поле `deleted_at`.

### Панель разработчика

Карточка задачи разработчика содержит:

- имя клиента;
- email клиента;
- название проекта;
- дату создания ТЗ;
- текущий статус;
- текст ТЗ;
- GitHub repository URL;
- кнопку «Задача выполнена».

После сдачи задачи статус проекта переводится в `review`, а менеджер получает уведомление.

### Чаты

Добавлены изолированные каналы коммуникации:

- `manager_client` — менеджер ↔ клиент в рамках проекта;
- `manager_developer` — служебный чат менеджер ↔ разработчик;
- `director_user` — директор ↔ пользователь.

API чатов: `/api/chats`.

Контроль доступа реализован на уровне API:

- клиент видит только свои проекты;
- разработчик общается по проекту только с менеджером;
- директор может создавать канал с любым пользователем.

### Панель директора

Добавлена страница `/director` и API `/api/director/dashboard`.

Директор видит:

- количество активных проектов;
- количество завершённых проектов;
- количество активных задач;
- среднюю оценку клиента;
- пользователей по ролям;
- список пользователей;
- audit log;
- список проектов в режиме просмотра.

Директор может:

- назначить роль `client`, `manager`, `developer`;
- заблокировать пользователя;
- снять блокировку;
- выполнить soft delete пользователя.

Все действия записываются в `audit_log`.
